## VTuber配信における「リアルタイム体験価値」の可視化プロジェクト

このリポジトリでは、**VTuber配信における「リアルタイム体験価値」** をテーマとした個人プロジェクトをまとめています。  
複数のVTuber事務所の総合職応募の際に、共通して提出できるポートフォリオとして作成しました。

大学の情報通信系の授業で学んだネットワーク計測・可視化を土台にしつつ、  
それを授業内の課題に留めるのではなく、**自分が好きなVTuberの配信体験**と結びつけて、  
「現場で本当に役立つかもしれない形」まで発展させたいと考えたことが、本プロジェクト着手の背景です。

エンジニアとしての実装力そのものよりも、  
**「技術を理解しながら、事業や体験の価値をどう設計するか」** をお伝えすることを目的としています。

---

## ■ プロジェクト概要

本プロジェクトは、VTuber配信における「リアルタイム体験の価値」を  
技術的側面から構造的に理解することを目的に制作しました。

配信ビジネスにおいて、タレントの魅力はもちろん重要ですが、  
その魅力が最大化されるかどうかは **「視聴体験の質」** に大きく依存しています。  
特に、コメントとの掛け合いやコール＆レスポンスが発生するVTuber配信では、  
数百ミリ秒単位の遅延やジッタ（揺らぎ）が体験価値に直結します。

本ツールでは、配信遅延を擬似的に再現・可視化することで、
**「低遅延設計がどのようにファン体験へ影響を与えるか」** を定量的に捉えることを目指しました。

---

## ■ 背景：なぜ「遅延」に着目したのか

VTuber配信は、

> 配信者 → 配信基盤 → 視聴者 → コメント → 配信者

という、双方向の循環構造を持つエンターテインメントです。

この循環の中で、

- コメントが **0.5秒** 遅れる世界  
- コメントが **1.5秒** 遅れる世界  

では、配信のテンポや熱量が大きく変わります。

好きなVTuberの生配信を視聴する中で、  
「今日はラグが少なくて掛け合いが気持ちいい」「今日は少し遅れている気がする」といった体感の差を覚え、  
その裏側にある技術的な要因を自分なりに理解したいと感じたことも、本テーマを選んだ動機のひとつです。

私は、配信体験の裏側にある技術的要素を理解することで、  
**IPの価値を支える構造そのものを把握したい** と考え、本プロジェクトに取り組みました。

---

## ■ アプローチ

### 1. ネットワーク遅延の取得

- C言語で RAWソケット を用いた `ping` / `traceroute` を実装  
- ICMP Echo を利用し、RTT（往復遅延） をミリ秒単位で取得  
- 経路可視化により、ネットワーク構造やボトルネックの把握を可能に

### 2. Webダッシュボードによる可視化

- Flask + WebSocket によるリアルタイム通信  
- JavaScript + Chart.js による遅延グラフ表示  
- 疑似コメントサーバを実装し、  
  「コメント送信からUI反映までの遅延」を可視化

### 3. 疑似配信環境の再現

- 配信プラットフォームを想定したターゲットIP設定  
- コメント受信遅延をUI上で直感的に表示  
- RTTの揺らぎ（ジッタ）をリアルタイムで確認できる環境を構築

---

## ■ 技術構成（概要）

- **C**：RAWソケット / ICMP制御  
- **Python**：Flask / Flask-SocketIO  
- **JavaScript**：リアルタイムグラフ描画  
- **Linux環境**での低レイヤーネットワーク制御

単なるライブラリ利用ではなく、  
授業で扱ったネットワークの基礎知識をベースにしながら、  
ネットワークスタックの挙動をコードレベルで理解することを重視しました。  
そのうえで、総合職としては **「技術を前提に置きつつ、事業側の議論に使える形にまとめる」** ことを意識しています。

---

## ■ 本プロジェクトから得た事業的示唆

### ① 低遅延設計は「技術課題」ではなく「事業課題」

遅延はUXに直結し、  
UXはエンゲージメント・視聴時間・投げ銭などの収益性にも影響します。

そのため、配信品質の設計は、  
**インフラの最適化にとどまらず、IP成長戦略の一部** であると感じました。

### ② グローバル展開とレイテンシ設計の関係

海外展開を行う場合、リージョン間遅延が大きな要素となります。

将来的には、

- 日本 / 北米 / 欧州間での遅延差  
- 配信モード別バッファ戦略  

などを統合的に設計する必要があると考えました。  
これは、**グローバルファンに対してどのようなリアルタイム体験を提供するか** という、事業戦略そのものにも関わる論点です。

### ③ ジッタとバッファリングのトレードオフ

低遅延を追求するほど、ジッタ（揺らぎ）への耐性は下がります。

- どこまでリアルタイム性を重視するのか  
- どの程度のバッファを持ち、安定性を優先するのか  

といった判断は、単なる技術判断ではなく、  
**ブランド体験・タレント体験の設計判断** であると理解しました。

---

## ■ 今後の拡張案

- 配信プラットフォーム別の遅延モデル導入  
- 複数拠点（日本 / 北米 / 欧州など）からの同時計測  
- コメント遅延の統計的分析（何％のコメントが何秒以内に返せているか等）  
- Docker化・CI導入による再現性・保守性の向上

これらを通じて、  
**「配信品質を定量的に語れる環境」** を整え、  
企画・運営・技術の三者で共通認識を持てる状態を目指したいと考えています。

---

## ■ 自己PR

本プロジェクトを通じて、私は  
**「エンターテインメント体験は、技術・企画・運営が統合されて初めて成立する」**  
という構造を強く実感しました。

大学で学んだ情報通信技術を起点に、  
好きなVTuberの配信体験に自分なりの問いを立て、  
「なぜこのラグが起きるのか」「どうすれば体験価値を高められるのか」を、  
データとプロトタイプを通じて検証しようとした点が、このプロジェクトの核です。

私は、技術そのものを極めるエンジニアというより、  
**技術理解を土台に、タレント・ファン・社内外の関係者を横断しながらプロジェクトを推進できる総合職**  
を目指しています。

将来的には、

- リアルタイム体験の設計  
- グローバル展開を見据えた配信基盤の方針検討  
- IP横断の企画・プロジェクトマネジメント  

といった領域に関わりながら、  
VTuberをはじめとしたデジタルIPの価値を、国内外へ拡張していく役割を担いたいと考えております。

## 3. 画面の見方と配信との関係

### (1) 配信環境（疑似）設定パネル

- **Target IP (配信サーバ想定)**  
  - 実際の配信では、配信ソフト → 配信プラットフォーム（例: YouTube, ニコニコ等）→ 視聴者という経路になります。  
  - このツールでは、その「配信プラットフォームの入り口」に相当する IP を擬似的に指定し、RTT を測定します。  
- **計測開始ボタン**  
  - クリックすると WebSocket 経由でサーバに計測要求を送り、1 秒ごとに `ping` を実行して RTT を取得します。  


### (2) 配信遅延グラフ（RTT）

- C 言語で実装した `ping` 実行ファイルを、Flask-SocketIO のバックグラウンドタスクから 1 秒ごとに実行  
- 標準出力 `PING <ip>: time=XX.XX ms` を正規表現でパースし、RTT(ms) を取得  
- JavaScript + Chart.js で、最新 60 点程度の RTT をラインチャートとして表示  

**ここで見えるもの**  
- ネットワークの混雑による RTT の揺らぎ（ジッタ）  
- 配信の「低遅延モード / 通常モード」の違いを模した、遅延レベルの変化（接続先を変えることで再現可能）  

### (3) コメントサーバ（疑似）からのコメント

- Flask-SocketIO 側で、数秒おきに疑似コメントを生成する「コメントサーバ」を実装  
- 各コメントには「サーバ送信時刻（sent_at）」が付与されます  
- フロントエンドでは、受信した時刻との差分を計算し、「受信遅延: XXX ms」として表示  

**VTuber 配信とのつながり**  
- 実際の現場では、  
  - 配信者が話す  
  - 配信サーバでエンコード・配信  
  - 視聴者側でデコード・バッファリング  
  という流れで遅延が蓄積されます。  
- 本ツールでは、コメントサーバを擬似実装することで、  
  「サーバ側でコメントが発生してから、視聴者側 UI に届くまでの遅延」を数値で意識できるようにしています。

## 4. 実装のポイント（技術的な観点）

### C 言語側（`tool_program/`）

- RAW ソケット + ICMP ヘッダ構造体を直接扱い、ICMP Echo Request / Reply を送受信  
- `utils.c` にて  
  - Internet Checksum の自前実装  
  - `gettimeofday` を用いた高精度な時間差計測（ミリ秒単位）  
- これにより、Linux の低レベルネットワークスタックの挙動を、教科書レベルではなく、実際のコードとして理解しています。  

### Web アプリ側（`web_app/`）

- `Flask` + `Flask-SocketIO` + `eventlet` により、  
  - Web サーバ
  - WebSocket サーバ
  を一体で構成  
- バックグラウンドタスク  
  - 各クライアントごとに 1 本の計測タスクを起動し、1 秒ごとに `ping` を実行  
  - 非同期 sleep（`socketio.sleep`）を使うことで、他クライアントとの共存を実現  
- フロントエンド  
  - `Chart.js` によるシンプルなリアルタイムグラフ描画  
  - WebSocket イベントを受け取り、グラフとコメントリストを即時更新

## 5. このツールから読み取れる「低遅延配信」への理解

- **RTT と配信遅延の関係**  
  - RTT 自体は「往復遅延」ですが、配信では「片方向遅延」×複数ステージ（エンコード/配信/デコード）として現れます。  
  - 本ツールでは RTT を「配信経路全体の一部」として捉え、変動を見ることで「ラグの揺らぎ」を体感できます。  

- **ジッタとバッファリング戦略**  
  - RTT が安定していない場合、プレイヤー側でどの程度バッファを持つべきか（= どこまで低遅延を攻められるか）という設計につながります。  

- **コメント反映の UX**  
  - コメントが 500ms 遅れる世界と、1500ms 遅れる世界では、配信者と視聴者の会話テンポが大きく変わります。  
  - 本ツールは、その差分を UI 上で直感的に比較できるようにしています。

- **配信プラットフォーム固有の遅延モデルを取り込む**

  - コンテナ化して誰でもすぐに立ち上げられるようにする。
